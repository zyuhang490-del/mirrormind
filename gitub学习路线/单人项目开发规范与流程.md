# 单人项目开发规范与流程

> 适用于 MirrorReader / MirrorMind，也适用于其他个人 Python 项目。

单人项目开发最重要的不是一个人提前学完所有技术，而是建立一套可重复的闭环：

```text
明确问题 → 限定范围 → 拆分任务 → 编码
→ 测试 → 提交 → 实际使用 → 收集问题 → 迭代
```

## 一、现阶段必须掌握的基础技能

### 1. Python 编程基础

- 变量、判断和循环；
- 字符串、列表和字典；
- 函数；
- 文件读写；
- JSON；
- 异常处理；
- 模块和导入；
- 基本路径操作。

不需要学完 Python 才开始。项目用到哪里，就补到哪里。

### 2. 命令行与开发环境

需要理解：

- 当前目录是什么；
- 如何运行 Python 文件；
- 如何创建和启用虚拟环境；
- 如何安装依赖；
- 如何阅读终端报错。

常见命令：

```powershell
python main.py
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install pytest
```

### 3. Git 与 GitHub

初期至少掌握：

```text
git status       查看当前变化
git diff         查看具体修改
git add          选择准备提交的内容
git commit       保存一个版本
git log          查看提交历史
git push         上传远端仓库
```

单人项目初期可以直接在 `main` 分支小步提交，不必立刻学习复杂的分支、合并和变基。

### 4. 调试能力

遇到错误时：

1. 完整阅读报错；
2. 找到最先属于自己代码的位置；
3. 检查输入数据；
4. 打印关键变量；
5. 缩小到最小复现；
6. 一次只修改一个原因；
7. 修复后重新测试原场景和相邻场景。

调试能力往往比记住更多语法更重要。

## 二、项目开发基本规范

### 1. 先写需求，后写代码

把功能描述成用户行为：

```text
作为阅读者，
我希望退出程序后保存位置，
从而在下次打开时直接继续。
```

同时写出验收条件：

```text
给定用户读到第 8 段，
当用户退出并重新打开，
那么程序从第 8 段恢复。
```

### 2. 明确非目标

每个版本都要写清楚暂时不做什么。例如 MirrorReader V0 不做：

- 自动情绪识别；
- PDF 和网页解析；
- 图形界面；
- 向量数据库；
- 云同步；
- 自主 Agent。

非目标不是永远放弃，而是防止当前版本失控。

### 3. 使用清楚的命名

推荐：

```python
current_position = 5
article_paragraphs = []
save_reading_state()
```

避免：

```python
a = 5
data = []
do_it()
```

函数名通常使用动词，变量名应说明其保存的内容。

### 4. 一个函数承担一个主要职责

例如：

```python
load_article()
split_paragraphs()
display_paragraph()
save_state()
```

不要把读取文件、显示内容、接收命令和保存数据全部塞进一个巨大函数，也不要为了显得专业而过早拆出几十个小函数。

### 5. 统一代码格式

Python 遵循 PEP 8 的基础规则：

- 使用 4 个空格缩进；
- 变量和函数使用 `snake_case`；
- 类使用 `PascalCase`；
- 常量使用 `UPPER_CASE`；
- 删除无用代码和无用导入；
- 文件结尾保留换行。

以后可以使用 Ruff 自动检查，初期先养成基本习惯。

### 6. 给出可理解的错误提示

至少考虑：

- 文件不存在；
- 文件为空；
- JSON 损坏；
- 用户输入未知命令；
- 阅读位置越界。

错误信息应告诉用户下一步怎么办：

```text
无法找到文章文件，请检查路径是否正确。
```

### 7. 保护隐私、密钥和版权内容

- API Key 不写进代码；
- 使用环境变量或 `.env`；
- 把 `.env` 加入 `.gitignore`；
- 私人阅读数据不上传 GitHub；
- 提交前查看 `git diff`；
- 不公开提交受版权保护的完整文章。

### 8. 保持文档与代码同步

最小项目建议包含：

```text
README.md       项目介绍和运行方法
TASKS.md        当前任务和下一步
docs/           详细设计说明
.gitignore      不应提交的文件
```

功能改变后及时更新说明，避免代码与文档互相矛盾。

## 三、测试规范

测试不是项目结束后的附加工作，而是功能的完成条件。

### 1. 初期人工测试

每次修改后检查：

- 正常输入能否运行；
- 空输入会怎样；
- 错误命令会怎样；
- 第一段继续按“上一段”会怎样；
- 最后一段继续按“下一段”会怎样；
- 关闭程序后能否恢复。

### 2. 后续自动测试

优先测试没有用户交互的纯函数：

```python
def split_paragraphs(text):
    ...
```

示例：

```python
def test_split_paragraphs():
    text = "第一段\n\n第二段"
    assert split_paragraphs(text) == ["第一段", "第二段"]
```

逐渐学习：

- `assert`；
- `pytest`；
- 正常、边界和错误情况；
- 如何让函数更容易测试。

## 四、单人项目的一般开发流程

### 第一步：定义问题

回答四个问题：

- 谁遇到了什么问题？
- 现在为什么解决不了？
- 最大阻力是什么？
- 如何判断问题得到改善？

MirrorReader 的核心问题是：

> 用户中断阅读后难以恢复认知上下文，并且固定的学习工具不能适应不同状态。

### 第二步：确定最小版本

只选择能够验证核心假设的功能：

```text
读取文章
→ 翻页
→ 保存位置
→ 恢复位置
→ 选择模式
→ 保存认知快照
```

### 第三步：设计数据和交互

开发前先回答：

```text
输入是什么？
程序内部保存什么？
输出是什么？
失败时怎么办？
```

不需要第一天就设计最终架构。

### 第四步：初始化项目

建立最小结构：

```text
README.md
main.py
sample_data/
tests/
.gitignore
```

初始化 Git，并完成第一次提交。

### 第五步：拆成小任务

一个任务最好能在一两次开发中完成：

```text
[ ] 读取 TXT
[ ] 按空行切分
[ ] 显示当前段落
[ ] 实现下一段
[ ] 实现上一段
[ ] 保存位置
[ ] 恢复位置
```

避免“完成阅读系统”这种无法直接执行和验收的任务。

### 第六步：完成最小纵向闭环

先让一条完整路径运行：

```text
读取文章 → 显示第一段 → 用户退出
```

然后逐步扩展。不要同时搭建多个复杂模块，却没有任何路径能够真正运行。

### 第七步：测试并提交

每完成一个独立功能：

```text
运行程序
→ 测试正常和边界情况
→ 查看 git diff
→ 提交
```

提交信息应说明做了什么：

```text
feat: save reading position
fix: prevent paragraph index overflow
docs: explain v0 scope
test: cover paragraph splitting
```

### 第八步：真实使用

开发者自己连续使用若干次，记录：

- 哪一步麻烦；
- 哪个功能没有价值；
- 哪个错误反复出现；
- 哪些原先假设不成立。

MirrorReader 至少经过 7 次真实阅读会话，再决定是否接入 AI。

### 第九步：发布一个版本

满足完成标准后：

- 整理 README；
- 清理调试代码；
- 运行全部测试；
- 创建例如 `v0.1.0` 的版本标签；
- 写清已知问题；
- 保存演示截图或录屏。

发布不一定意味着马上给很多人使用，而是为当前阶段画出明确边界。

### 第十步：复盘并进入下一轮

回答：

```text
原假设是什么？
真实结果是什么？
什么有效？
什么无效？
下一版本只解决哪个问题？
```

## 五、任务完成定义（Definition of Done）

一个任务同时满足以下条件才算完成：

- 功能符合验收条件；
- 正常情况能够运行；
- 关键边界已经测试；
- 没有提交隐私数据和密钥；
- 代码命名清楚；
- 文档已经同步；
- 已产生一次 Git 提交；
- 开发者能够解释核心代码。

AI 生成并成功运行，不等于真正完成开发。能够解释、修改和排错，才算掌握。

## 六、AI 辅助编程规范

向 AI 提问时提供：

- 想实现的功能；
- 当前掌握的知识；
- 当前代码；
- 完整报错；
- 已经尝试过的方法。

不要一次要求 AI 生成完整项目。优先要求它：

1. 解释需要的知识；
2. 把任务拆小；
3. 提供最小示例；
4. 给出练习，让自己完成核心部分；
5. 对自己的代码做检查和解释。

接受 AI 代码前，至少能回答：

- 每个函数负责什么；
- 数据从哪里进入、到哪里保存；
- 修改哪个变量会改变行为；
- 出错时最可能在哪一层。

完全回答不了时，说明代码超过当前可控范围，应继续拆小。

## 七、以后逐步补充的技能

按照项目需要逐渐学习：

1. `pytest` 与自动测试；
2. HTTP、API 和 JSON；
3. 数据库与 SQL；
4. 日志系统；
5. 类型标注；
6. 后端框架；
7. Docker；
8. Linux；
9. CI/CD；
10. 部署与监控；
11. 性能和安全；
12. 团队协作与代码审查。

## 八、现阶段最重要的原则

> 每次只解决一个明确问题，写出能运行的小功能，验证后保存版本，并确保自己理解它。
