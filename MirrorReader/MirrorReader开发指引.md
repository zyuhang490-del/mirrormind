# MirrorReader 开发指引

> 面向当前阶段的 MirrorMind 最小原型。目标不是立刻制造完整的“个人认知操作系统”，而是通过一个真实、可运行的小项目，验证“认知连续性”和“工具随状态改变”是否能降低学习阻力。

## 1. 项目定位

MirrorReader 是一个能够保存阅读进度、记录当时认知状态，并根据本次状态改变阅读方式的个人阅读工具。

它首先服务于一个真实场景：阅读《经济学人》、技术文章或课程材料时，用户因为材料难、目标模糊、查阅步骤分散以及中断后难以恢复而放弃。

MirrorReader 不替用户决定人生目标，也不追求一次性解决所有学习问题。它先解决三个可验证问题：

1. 中断后能否快速回到上一次的认知现场；
2. 同一份材料能否根据当下状态采用不同学习结构；
3. 阅读过程中的疑问、表达和想法能否在未来重新发挥作用。

## 2. 核心设计原则

### 2.1 允许目标模糊

用户可以只说“我想学这篇文章”，不必预先决定是背单词、学句型还是分析思想。系统通过实际阅读过程帮助目标逐渐形成。

### 2.2 保留人的决定权

系统可以建议本次模式，但第一版由用户主动选择。不要在没有证据的情况下声称系统已经“识别”了用户情绪或认知状态。

### 2.3 保存过程，而不只保存结果

除了阅读位置，还应保存：本次模式、疑问、兴趣点、中断原因和下一次入口。

### 2.4 先降低阻力，再增加智能

如果不调用大模型的版本都不能让阅读更容易，加入 AI 只会掩盖产品问题。

### 2.5 不优化沉迷指标

不以打开次数、停留时间或连续签到作为最高目标。优先衡量是否更容易继续、是否产生实际理解和输出。

## 3. 第一版明确不做什么

V0 暂时不做：

- 自动识别情绪或认知状态；
- 摄像头、键盘和屏幕监控；
- PDF、网页抓取和 OCR；
- 登录、云同步和多用户；
- 向量数据库和知识图谱；
- 自动生成复杂笔记；
- Electron 或完整图形界面；
- 自动操作其他软件；
- 自主 Agent。

这些能力不是永远不做，而是不应该阻塞第一个可验证版本。

## 4. V0 用户体验

一次完整使用流程如下：

```text
启动程序
  ↓
选择一篇本地 TXT 文章
  ↓
程序恢复上次位置和状态
  ↓
用户选择本次模式：轻松 / 正常 / 深入
  ↓
逐段阅读，随时记录生词、疑问或想法
  ↓
结束时填写一句“为什么停下”
  ↓
程序自动生成下一次入口并保存认知快照
```

再次打开时，程序应直接提示：

```text
上次读到第 12 段。
当时采用“正常学习”模式。
你关注了作者表达因果关系的句式。
你因为需要上课而结束。
建议入口：继续第 13 段，或先回顾上次保存的句式。
```

## 5. 三种阅读模式

V0 不需要让三种模式拥有复杂算法。只要界面和提问方式不同，就能验证“自结构”的雏形。

### 5.1 轻松阅读

- 每次显示较长内容；
- 不主动要求查词；
- 只保留“记下这个”和“继续”；
- 目标是维持接触和连续性。

### 5.2 正常学习

- 每次显示一个段落；
- 可以记录生词、句型和疑问；
- 每几段询问一次是否需要总结；
- 目标是理解内容并积累少量表达。

### 5.3 深入分析

- 每次显示一个段落；
- 提示观察论点、证据、结构和表达；
- 允许写较长分析；
- 目标是形成可输出的理解。

第一版由用户选择模式。以后可以根据时间、历史选择和用户反馈给出建议，但仍允许一键修改。

- [ ] 支持上一段、下一段；
- [ ] 退出后保存阅读位置；
- [ ] 再次打开时恢复位置；
- [ ] 开始时选择阅读模式；
- [ ] 记录 `生词 / 疑问 / 想法`；
- [ ] 结束时记录中断原因；
- [ ] 自动写入一次认知快照；
- [ ] 数据仅保存在本地 JSON 文件。

### 完成后再考虑

- [ ] 搜索历史记录；

- [ ] 根据历史推荐旧片段；
- [ ] 图形界面。

## 7. 推荐目录结构

起步时保持简单：

```text
MirrorReader/
├── README.md
├── main.py
├── sample_data/
│   └── sample_article.txt
├── private_data/
│   ├── articles/
│   └── reader_state.json
├── tests/
│   └── test_reader.py
└── .gitignore
```

第一阶段只写 `main.py`。当它超过约 150～200 行，或者你已经感到某些代码职责混乱时，再拆成：

```text
MirrorReader/
├── main.py          # 程序入口和命令循环
├── reader.py        # 文章切分、翻页
├── storage.py       # JSON 读取与保存
├── session.py       # 阅读会话和认知快照
└── tests/
```

不要为了看起来“专业”而过早拆分十几个文件。

V0 使用一个 JSON 文件即可：

```json

  "articles": {

      "total_paragraphs": 36,
      "last_mode": "normal",
      "next_entry": "继续第 13 段，关注因果表达",
      "notes": [
        {
          "type": "expression",
          "paragraph": 10,

      ],
      "sessions": [
        {
          "started_at": "2026-08-02T20:00:00",

          "mode": "normal",
          "start_position": 7,
          "end_position": 12,
```

这不是最终数据结构，只是够用的第一版。不要为了未来所有可能性设计复杂数据库。

## 9. 命令行交互建议

阅读时可以提供以下命令：

```text
n                 下一段
p                 上一段
w 单词            记录单词或表达
q 内容            记录疑问
i 内容            记录想法
s                 查看当前进度
notes             查看本篇笔记
exit              保存并退出
help              查看帮助
```

命令解析可以从最简单的字符串判断开始：

```python
command = input("> ").strip()

if command == "n":
    ...
elif command.startswith("w "):
    ...
```

这会自然练习循环、判断、字符串和函数，非常适合你现在的阶段。

## 10. 分阶段开发路线

不要按照日期硬赶进度。每一阶段通过验收后再进入下一阶段。

### 阶段 0：把问题说清楚

产物：`README.md`

写清楚：

- 你为什么没有坚持阅读；
- MirrorReader 准备减少哪些阻力；
- V0 做什么、不做什么；
- 如何运行程序。

学习点：项目意识、需求边界、Markdown。

验收标准：没有代码的人也能看懂这个项目解决什么问题。

### 阶段 1：可以连续翻页

任务：

1. 用 `open()` 读取 TXT；
2. 使用字符串切分段落；
3. 用 `while` 循环接收命令；
4. 用变量保存当前位置；
5. 实现上一段、下一段和退出。

学习点：文件、字符串、列表、循环、判断、索引。

验收标准：能从头到尾阅读示例文章，且不会越过第一段和最后一段。

### 阶段 2：退出后可以继续

任务：

1. 学习字典；
2. 使用 `json` 模块保存当前位置；
3. 启动时检查状态文件是否存在；
4. 如果存在则恢复；
5. 如果损坏则给出可理解的错误信息。

学习点：字典、JSON、路径、异常处理、函数。

验收标准：关闭终端并重新打开，仍从正确段落继续。

### 阶段 3：保存认知快照

任务：

1. 开始时选择轻松、正常或深入模式；
2. 支持记录生词、疑问和想法；
3. 退出时询问中断原因；
4. 保存开始位置、结束位置、关注点和下一入口；
5. 再次启动时显示上次快照。

学习点：函数拆分、列表中的字典、时间处理、输入验证。

验收标准：隔一天再次打开时，不需要回忆上次为什么停下。

### 阶段 4：让三种模式真的不同

任务：

- 轻松模式减少问题和操作；
- 正常模式显示常用记录入口；
- 深入模式提示论点、证据和表达结构；
- 记录用户是否中途切换模式。

学习点：程序状态、配置字典、减少重复代码。

验收标准：同一篇文章在三种模式下具有明显不同的使用体验。

### 阶段 5：第一次真实验证

连续使用 7～14 次，不要求每天签到。每次结束记录：

- 启动到真正开始阅读花了多久；
- 阅读了几段；
- 是否顺利恢复上下文；
- 哪一步仍然麻烦；
- 系统是否增加了额外负担；
- 有没有产生可复用的表达或想法。

验收标准：能够基于真实记录说出“哪项功能有效、哪项无效”，而不是只说“感觉不错”。

## 11. 测试清单

开始可以人工测试，不必立刻学习完整测试框架。

### 文件测试

- 空文件；
- 只有一个段落；
- 中文与英文混合；
- 文件不存在；
- 编码错误。

### 翻页测试

- 第一段继续按上一段；
- 最后一段继续按下一段；
- 输入未知命令；
- 输入空字符串。

### 状态测试

- 第一次运行，没有 JSON 文件；
- 正常保存后重新启动；
- JSON 内容缺少某个字段；
- JSON 文件损坏；
- 切换到另一篇文章后再返回。

阶段 2 完成后，可以学习 `pytest`，优先测试“段落切分”和“进度恢复”两个纯函数。

## 12. Git 使用方式

不要等全部完成后才提交。一个功能完成并能运行，就提交一次：

```text
docs: describe MirrorReader v0 scope
feat: load and split text article
feat: navigate between paragraphs
feat: save reading position to json
feat: restore previous reading session
feat: record words questions and ideas
fix: prevent position from exceeding article range
```

每次提交前做三件事：

1. 自己运行一次；
2. 查看 `git diff`；
3. 确认没有 API Key、私人文章和个人记录。

建议 `.gitignore` 至少包含：

```gitignore
__pycache__/
.venv/
private_data/
.env
```

《经济学人》文章可能涉及版权，不要把完整文章公开提交到 GitHub。仓库中只放自己编写或明确允许使用的示例文本。

## 13. 如何使用 AI 辅助开发

AI 可以当老师和结对伙伴，但不要让它一次生成整个项目。推荐提问方式：

```text
我刚学完 Python 循环，现在需要把一篇文本按空行切成段落。
请先解释需要哪些知识，再给我一个不超过 15 行的示例。
不要替我完成整个项目，给我一个练习让我自己写。
```

遇到错误时提供：

- 你想实现什么；
- 当前代码；
- 完整报错；
- 你已经尝试过什么。

每次接受 AI 代码前，至少能回答：

1. 每个函数负责什么；
2. 数据从哪里进入、到哪里保存；
3. 修改哪个变量会改变行为；
4. 出错时最可能在哪一层。

如果完全回答不了，就说明生成的代码超过了当前可控范围，应拆小。

## 14. V1：接入大模型，但保持克制

V0 验证有效后，再加入一个 OpenAI 兼容 API。第一批 AI 功能只建议做：

1. 根据当前段落解释用户主动选择的表达；
2. 根据模式生成不同深度的解释；
3. 会话结束时，把用户已经记录的内容压缩成下一入口。

不要默认让模型总结全文。全文总结很容易让用户跳过阅读，也无法验证 MirrorReader 是否真正帮助理解。

AI 输出应尽量使用固定 JSON 结构，例如：

```json
{
  "meaning_in_context": "",
  "common_usage": "",
  "example": "",
  "one_question": ""
}
```

API Key 只放在环境变量或 `.env`，绝不能写进代码或提交到 Git。

## 15. V2：灵接的最小实验

当积累了一定数量的阅读快照后，再测试“过去与现在共振”。第一版不必上向量数据库，可以先使用简单规则：

- 相同关键词；
- 相同笔记类型；
- 相同关注主题；
- 过去未解决的问题；
- 曾经标记为“以后想用”的表达。

系统可以呈现：

```text
你现在正在分析“技术如何影响人的主动性”。
17 天前阅读另一篇文章时，你记录过一个相反判断。
是否并排查看？
```

验证用户确实愿意使用这种连接后，再考虑嵌入模型和向量检索。技术应该跟随已验证的需求。

## 16. V3：从 MirrorReader 回到 MirrorMind

MirrorReader 验证成功后，可以抽象出 MirrorMind 的通用组件：

```text
阅读材料             → 当前任务对象
阅读模式             → 显式认知状态
阅读进度             → 任务连续性
会话快照             → 全储存层的认知快照
历史片段重新出现      → 灵接
不同模式下的界面变化   → 自结构雏形
单词解释和笔记工具     → 原子能力调用
```

届时再把“阅读”替换为编程、写作或研究任务，检验相同架构能否复用。

## 17. 评估指标

不要使用单一分数声称“创造力提高了”。V0 记录以下可观察指标即可：

- 恢复成本：打开程序到开始阅读所需时间；
- 连续性：中断后是否能准确接回；
- 完成情况：每次实际阅读段落数；
- 有效沉淀：产生了多少后来真正使用的表达或想法；
- 工具摩擦：一次阅读需要切换多少外部工具；
- 主观负担：结束时用 1～5 分记录“系统是否增加负担”；
- 输出转化：阅读材料是否进入仿写、文章、代码或项目决策。

成功不等于每天使用，而是：当用户决定回来时，系统能接住他。

## 18. 主要风险

### 风险一：重新造一个复杂笔记软件

应对：所有功能都问一句——它是否缩短了“恢复和继续”的路径？不能证明就暂不加入。

### 风险二：AI 帮得太多，用户没有真正学习

应对：默认只解释用户主动选择的部分，并鼓励先表达自己的理解。

### 风险三：记录行为本身成为负担

应对：允许什么都不记录；退出时只要求一句中断原因，其余字段可选。

### 风险四：把状态识别包装成读心

应对：V0 使用用户选择；未来使用可解释的行为证据，并始终显示不确定性。

### 风险五：项目过早膨胀

应对：完成 V0 的真实使用验证以前，不增加网页端、移动端、向量数据库和自动 Agent。

## 20. V0 完成定义

只有同时满足以下条件，才算完成 V0：

- 一个新用户能根据 README 独立运行；
- 能阅读、翻页、保存和恢复；
- 能记录三类内容；
- 能保存并显示上一次认知快照；
- 三种模式至少在交互结构上不同；
- 对空文件、边界翻页和损坏状态有基本处理；
- 代码中没有密钥和私人材料；
- 至少进行 7 次真实阅读会话；
- 写出一份验证报告，说明有效、无效和下一步。

## 21. 现在就做的第一步

不要先安装大型框架。第一轮只做以下任务：

1. 在 D 盘创建 `MirrorReader` 项目目录；
2. 初始化 Git；
3. 创建 `README.md`、`main.py` 和一份可公开的示例文本；
4. 写一个程序读取文本并打印段落数量；
5. 提交第一次 Git 记录。

第一次代码目标应该小到可以在一次学习中完成：

```text
运行 main.py
→ 成功读取 sample_article.txt
→ 输出“共找到 N 个段落”
```

做到这里就停下来，确认自己理解每一行，再继续实现翻页。MirrorMind 的第一步不是更宏大的设计，而是一个你能解释、能修改、能持续迭代的程序。
